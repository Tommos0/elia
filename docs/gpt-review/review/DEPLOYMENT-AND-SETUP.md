## The design worth preserving

Elia separates a development trunk (`master`) from a running checkout (`live`) and gives its own chats branches and worktrees. A deploy runs under an application-owned runner, survives navigation away from Settings, rejects overlapping operations, reports steps, and keeps a record of loaded revisions. The plain recovery page can work without the main JavaScript bundle. Those are valuable controls for a program that edits itself. [Deployment contract](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/specs/deployment.md), [runner](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy/runner.ex), [recovery](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia_web/recovery.ex).

The actual operation moves the checkout to the candidate **before** fetching dependencies and running tests, then resets it on failure. Documentation sometimes describes the test gate as occurring before the fast-forward; the implementation's ordering is the one to reason about when assessing filesystem effects. Code modules are not reloaded on ordinary requests, but asset files are served from the filesystem independently of module loading. [Operation sequence](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1096-L1145), [static serving](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia_web/endpoint.ex#L31-L48).

## DEV-01 — Make the documented setup complete on a clean clone

### Evidence and trigger

The documented first-run sequence is `mix setup` followed by `mix phx.server`. Node is described as optional and needed for browser tests/previews. The `setup` alias fetches Mix dependencies, installs the asset tool binaries, and builds assets; neither it nor `assets.setup` installs `assets/package.json` dependencies. [README setup](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/README.md#L12-L38), [Mix aliases](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/mix.exs#L84-L104).

The main bundle unconditionally imports `terminal.js`, which imports `@xterm/xterm` and `@xterm/addon-fit`. CSS also directly imports xterm's stylesheet from `assets/node_modules`. Thus even a global JavaScript resolution workaround cannot supply the missing relative CSS file in a normal fresh checkout. `assets/node_modules` is ignored by Git. The explicit npm installation paths are preview and deployment, neither of which is part of the documented setup alias. [Entry point](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/assets/js/app.js#L20-L35), [terminal imports](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/assets/js/terminal.js#L11-L13), [stylesheet](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/assets/css/app.css#L1-L12), [preview installer](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/bin/preview#L24-L37), [deploy installer](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1231-L1238).

**Precondition:** a fresh clone without a warm local `assets/node_modules`. **Impact:** the advertised setup path lacks a necessary dependency step, so a contributor can reach an asset-build error before using the application. The local resolver check returned `MODULE_NOT_FOUND` for both packages. That is expected in a clone; the defect is the missing installer in the documented path. A full `mix setup` failure was not observed here because Mix is unavailable. [Recorded check V07](../evidence/static-checks.json).

### Repair and acceptance

Choose one supported setup entry point and make it install the locked Node dependencies before building. The existing lockfile makes a reproducible clean install practical. Update the prerequisites so source asset builds require Node/npm; distinguish them from running a previously built bundle if that mode is supported. Keep the preview and deployment paths consistent with this decision.

Test the literal README sequence in a clean checkout with no `node_modules`, no application build artifacts, and isolated state. Require nonempty JS/CSS bundles, no unresolved imports, an HTTP page that loads its assets, and a working terminal hook. Run a second setup to establish repeatability. This is an integration acceptance check, not a unit test asserting that an alias contains a particular string. Relevant contracts: TERM-12, BROWSER-2, PREVIEW-14, DEPLOY-19; the setup documentation needs a clear owning requirement.

## DEP-01 — Roll back the bytes users are actually served

### Evidence and trigger

The deploy builds directly into the live tree's `priv/static/assets/js/app.js` and `priv/static/assets/css/app.css`. Those generated paths are Git-ignored. If the build fails or the subsequent bundle check detects a missing/empty entry point, `test_merged/3` calls `rollback_note/2`, which performs only a Git hard reset. The rollback operation's front-end failure path uses the same mechanism. [Build/check](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1170-L1249), [failure path](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1116-L1134), [reset implementation](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1260-L1269), [rollback failure](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L998-L1005), [ignored artifacts](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/.gitignore).

A build can overwrite one output and then fail on another, truncate a file, or delete an entry point. Resetting tracked source restores neither the previous generated output nor its dependency installation. The endpoint continues serving the same filesystem paths, and the layout references them directly. A rejected deploy can therefore leave the old BEAM code paired with new, partial, or missing assets. [Configured output paths](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/config/config.exs#L44-L64), [layout asset links](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia_web/components/layouts/root.html.heex#L14-L20).

**Qualification:** development watchers may eventually rebuild reverted sources. They are asynchronous, are not part of the rollback success check, and cannot guarantee a coherent bundle after dependency or build failure. This review does not claim every failed deploy permanently breaks the UI. It identifies an unprotected failure path and a period of incoherent serving. [Dev watchers](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/config/dev.exs#L16-L19).

The isolated V09 probe made a clean Git repository with an ignored generated asset, changed that asset for a candidate revision, and reset the tracked source. The old source returned, the candidate asset remained, and Git reported a clean tree. This verifies the Git/filesystem premise, not an executed Elia deployment. [Probe result](../evidence/static-checks.json), [reproduction script](../verification/reproduce-static-checks.py).

### Existing tests and contract

The missing/empty-bundle tests deliberately remove or empty an output, then assert that `live`/HEAD was restored and no loader ran. They do not assert restoration of the asset bytes a browser would fetch. More subtly, their `front_end_tree` fixture commits the bundle to Git, unlike the real application's ignored generated assets. A restoration assertion against that fixture alone could still hide the production failure. The failed-rollback test similarly verifies branch and loaded-revision state. [Fixture setup](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/test/elia/deployment_test.exs#L303-L310), [tests 1634–1682](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/test/elia/deployment_test.exs#L1634-L1682), [failed rollback test](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/test/elia/deployment_test.exs#L1873-L1935).

DEPLOY-5, DEPLOY-19, DEPLOY-24 and DEPLOY-26 describe a rejected candidate leaving the running application usable. Extend the contract to name the served bundle as part of what is restored. Git revision equality alone is insufficient evidence. [Failure guarantees](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/specs/deployment.md#L192-L231).

### Repair and acceptance

Prefer building a candidate bundle in a separate directory and promoting it only after validation, with a recoverable previous version. If staging is too large a change, snapshot and restore the current bundle around the operation and verify restoration before reporting recovery. Coordinate watchers with whichever transaction boundary is chosen. Include the package/dependency state in the design discussion; restoring CSS/JS alone does not prove that a future restart can compile the old lockfile.

Acceptance: serve known revision-A asset bytes; have a revision-B build write one new asset and then fail; assert both Git state and HTTP-served bytes remain A after rejection. Cover deletion, truncation, one-output success, missing-output success exit, failed rollback, and a deploy with no source commits to merge. Ensure the recovery route works throughout. Add an actual asset-pipeline smoke test in addition to injected build seams. No user data migration is inherently required, but any persistent bundle/deploy-record representation needs an explicit compatibility decision.

## DEP-02 — Do not equate hot-reload support with restart supervision

`Deploy.restartable?/0` claims to detect whether a manually launched server would stay down. It actually delegates to `hot_reload_available?/0`, which checks only that Mix is loaded and `code_reloader` is true. The common config enables the reloader for operating environments, including a bare `mix phx.server`. The restart path eventually calls `System.stop(75)`. [Capability check](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1033-L1054), [common config](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/config/config.exs#L24-L28), [stop path](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L879-L909), [System.stop default](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L1318-L1323).

**Trigger:** set up a clean `live`/`master` tree, start it directly with `mix phx.server`, and request Restart from Settings. The UI gates deployment readiness using repository state, not the existence of a restarting supervisor. After a successful deploy, the server stops; nothing in the bare launch starts a replacement. This is a false capability signal, not a demand that a server self-restart without a supervisor. DEPLOY-7 states the external-supervisor prerequisite; the README documents the supported `bin/serve` and service launches. [Settings controls](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia_web/live/settings_live.ex#L661-L696), [DEPLOY-7](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/specs/deployment.md#L130-L134).

Introduce an explicit supported supervisor marker/configuration or an equally reliable readiness check, set by `bin/serve` and documented for external supervisors. Use that separate capability in both UI and execution, and say how to launch correctly when absent. Do not infer it from Mix/reloader presence. Test a bare launch rejecting or clearly disabling Restart, a supervised launch replacing the process, and hot reload remaining available independently. Existing restart tests replace stopping with a message to the test process; keep them but add one process-level acceptance test in an isolated fixture. [Test seams](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/test/elia/deployment_test.exs#L205-L241).

## Follow-up questions, not extra findings

The worktree helpers fall back to the live/parent workspace on creation failure, which is documented behavior. Decide whether future isolation guarantees should distinguish an intentionally unconfigured setup from an unexpected worktree-creation error. Also test restoration across Mix dependency version changes: rollback currently rebuilds the front end without an explicit old-lockfile dependency fetch. Neither item was exercised end to end here, so they remain design/validation questions. [Workspace fallback](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L606-L621), [child fallback](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/tasks.ex#L243-L253), [rollback flow](https://github.com/Tommos0/elia/blob/5be0bd873bd2716529de25541efb1825495cd12e/lib/elia/deploy.ex#L930-L1005).

Before implementation, update the owning spec and follow the repository's approval workflow. The review does not modify or deploy the project.
