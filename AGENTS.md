# Elia

A local AI harness with a Phoenix LiveView chat UI. The agent works through skills and can change its own code behind guardrails. Module layout is in `README.md`. Features are specified in `specs/` (index and workflow in `specs/README.md`).

## Always

- This project is spec-driven. Before changing behaviour, update or add the spec in `specs/`. Then implement it and test each requirement you touched, citing its ID (e.g. `# SHELL-3`). Never renumber or reuse a requirement ID. When you add a spec, add it to the index table in `specs/README.md`. The rest of what the corpus must hold to — one word for `Status:`, a section outside the allowed shape, an ID defined twice, a citation of an ID no spec defines — is `specs/README.md`'s rules (SPEC), and `test/elia/spec_hygiene_test.exs` fails the suite on it, so a violation is a test failure rather than a review comment. Every requirement must also be accounted for by a test file that is there or by a `No test:` line in its own spec saying why (TRACE, `specs/test-traceability.md`), which `test/elia/spec_tests_test.exs` fails the suite on
- After drafting or updating a spec, stop and ask the user to approve it before implementing, unless the user explicitly asked to skip the spec approval for this change. Wait for that approval before touching code or tests
- When the user asks for work to be done with sub-tasks (`spawn_task`), this chat does the planning and writes the spec itself, and sub-tasks implement only: for a job that is worth more than one step and is understood up front, draft or update the spec in `specs/` here and get the user's approval first, then spawn one sub-task per implementation step, each brief naming the spec and the requirement IDs to satisfy (and saying to test what it touches, commit and report). Keep the spec to behaviour and requirement IDs and leave the internals to the sub-task, which should raise a spec that does not fit the code as a question instead of deviating silently. A small or exploratory job — one file, one obvious behaviour, or one whose spec is its result — is done in this chat instead. Never hand the spec-writing or the planning to a sub-task
- Number the sub-tasks you spawn — `001`, `002`, … in the order you spawn them in this chat — and hand the brief over as a file rather than as the `spawn_task` text: write `.tasks/<n>/brief.md` in the workspace root holding the title, the goal, the specs and requirement IDs to satisfy, the files, the constraints, what "done" means and the child's own chat id, and give the spawn little more than the absolute path of that file and of the `report.md` beside it ("Read `<path>` and follow the instructions. Write your report to `<that folder>/report.md`") — absolute, because the child works in your workspace (SUBTASK-23) but may `cd` within it (WD-1). The id is the one thing that has to wait, since `spawn_task` returns it only after that file is written: write the file first and add `child: <task_id>` to it once the spawn returns (the child knows its own id anyway — `$ELIA_CHAT_ID`, SHELL-14). A sub-task reports back in the same shape, `report.md` beside its `brief.md` — what it did, what it changed, anything the user must settle — written before it calls `mark_done`, so read `.tasks/<n>/report.md` as well as the `{"task_id", "summary"}` result `await_task` gives you. Neither file is work: don't commit them (`.tasks/` is ignored in this tree)
- A sub-task is an ordinary chat and ends when — and only when — its chat is marked done: its own `mark_done`, or the user's control in that chat (SUBTASK-33, `specs/subtasks.md`). Nothing else ends one — not the end of a turn, not a turn the user stops, not a limit it hits, not a session that dies — so a stopped turn leaves it running, with the parent still waiting (SUBTASK-16, SUBTASK-17, SUBTASK-24, SUBTASK-34). Stopping a parent's turn still stops the turn of every child it has running, the same way. A sub-task's status is its own chat's status, and nothing else about it is special: it has no limits, lock, listing or record of what it changed of its own, and the result a parent collects with `await_task` is `{"task_id", "summary"}`, which the harness derives (`SUBTASK-9`). Don't reintroduce a task status vocabulary (`running`, `blocked`, `failed`, `unfinished`, `cancelled`), a per-task watcher, a registry of running children or a per-task entry, a child-only step or time limit, a `finish_task` tool, a `list_tasks` listing (a parent lists its children with `list_chats`'s `children`, HIST-2) or a parent-side record of a child's commit and files
- In a sub-task chat, "done" means something smaller than it does here: the work is committed on your own branch (`chat/<sub-task id>`, DEPLOY-28), not landed on `master` — the parent merges it when it wants the work (SUBTASK-23) — and calling `mark_done` is your last act, because it is what ends the task and reports your result. So commit before you mark the chat done, and say what you did in your last message, where anything the user must settle also goes
- Use the `mix precommit` alias when you are done with all changes and fix any pending issues. Plain `mix precommit`: no command inherits `MIX_ENV`, so the alias's `preferred_envs` applies and it runs the tests in `test` (ISOL-24; see `docs/agents/elixir.md`). A test run is a `shell` call — there is no `run_tests` tool (VERIFY-11) — so give a suite run a longer `timeout_seconds` than the shell's default: a chat's first run in a fresh worktree compiles deps and app before its first test. Never run two test runs at the same time, in any worktree: they share `/tmp/elia-test-pN` and corrupt each other's `settings.dets` (`docs/agents/testing.md`, Running)
- Commit to git whenever you finish a feature (after tests/`mix precommit` pass). Use a `feat: <summary>` message (or `fix:`/`docs:` etc. as appropriate), and commit only that feature's changes. Never commit a half-finished feature
- When the user states a standing preference, rule or workflow ("whenever you…", "always…", "never…", "from now on…"), record it in this file (`AGENTS.md`) in the same turn, as a bullet under "Always" (or in the matching `docs/agents/` file if it is topic-specific, then say so here). Don't just acknowledge it verbally, since you won't remember it next session. Then tell the user which file and line you updated
- In one step, ask for everything you already know you need: a step's calls run at the same time (LOOP-10), so several reads, searches or shell commands in one message cost one model round trip, not several. Batch the lookups a change needs — the topic docs its row names, the files it will touch, the greps that locate them — rather than spending a round trip per file; a batched command still gets its own jail and its own `/tmp` and pid namespace (ISOL-2, ISOL-9, `specs/command-isolation.md`), so batching shell calls is safe
- Read, create, edit and search files with the file tools (`read_file`, `write_file`, `edit_file`, `search_files`), never with `shell` (`cat`, `sed`, `echo >`, heredocs, Python/other scripts, or `grep` to find text). `search_files` returns each match with its surrounding lines (FILE-24..FILE-30, `specs/file-tools.md`), so one call replaces `grep` plus the `read_file` that followed it. Use `shell` only to run programs such as `mix` and `git`. Shell edits skip the workspace policy and the user's file-change review
- Never prefix a shell command with `cd`. Every call already runs in the chat's working directory (`Elia.Skills.Shell` passes `cd: Elia.Workdir.of(ctx)` to `Elia.Shell.run/2`, SHELL-2, WD-9, `specs/working-directory.md`) — the workspace root until the `cd` tool moves the chat (`Elia.Skills.Workdir`, WD-1, WD-3) — each call is its own `bash -c` with no state carried over, and the tool's schema has no `cwd` argument — so `cd "$(pwd)" && …`, `cd . && …` and `cd <the workspace root> && …` all change nothing and only add noise to the command the user has to approve and read. To work somewhere else, call `cd` once (it also moves what the file tools' relative paths resolve against); a `cd` belongs in a command only when it *changes* tree for that one command (the live tree, a sibling worktree) or when driving a `terminal`, whose session persists between sends
- Shell commands run with `bash -c` where bash is installed, otherwise POSIX `sh -c` (SHELL-2, `Elia.Shell.shell/1`), so write commands that also work under `sh`: bash-only syntax such as `${PIPESTATUS[0]}`, `[[ ... ]]`, arrays and `set -o pipefail` fails where the shell is `sh`, and after a pipeline `$?` is the last command's status (a failing `mix test | tail` looks like a success). Prefer one command that reports the status you mean, and `bash -c '...'` explicitly only when you really need bash
- The dev server never reloads code on its own: a request recompiles and loads nothing, and a change to `lib/`, `config/` or `mix.exs` reaches the running app only through a *deploy*. **When a change is done, commit it in your worktree and merge that branch into the trunk yourself** — the recipe above (DEPLOY-13). Then mark the chat done with `mark_done` (`specs/chat-done.md`, DONE-6), so the chat list shows it as finished work rather than as a chat that was abandoned; a chat marked done is still resumable, and the user's next message reopens it (DONE-9). The harness never merges your branch. Deploying is the user's step, in the chat UI's Settings page: a deploy brings `master` to `live` (fast-forward, after the full test suite, then with the tree's Node packages installed and its assets rebuilt — DEPLOY-19) and loads it — "Hot reload", which recompiles and loads the live tree keeping running state, or "Restart", which restarts the server. So make all the edits for a change first, run the tests, then commit and merge; don't expect the change to be live until the user has deployed it
- When a change touches the UI (a template, `assets/css/`, `assets/js/` or a colocated hook), show the user what it looks like before it is deployed: run `bin/preview` in the chat's workspace and put the Markdown image links it prints into your reply. It screenshots the workspace's own code in a real headless browser, in the test env — no deploy, no API key — and its first run in a workspace builds assets and starts a browser, so give the `shell` call a longer `timeout_seconds` (PREVIEW-9, `specs/ui-preview.md`). Preview in dark mode at a mobile width by default — `ELIA_PREVIEW_THEME=dark ELIA_PREVIEW_WIDTH=390 bin/preview …` (PREVIEW-3, PREVIEW-13) — and take a light or desktop picture as well only when the change is about that
- A chat in Elia's own project works in the project's folder — the live tree the server runs from, where your files, `deps`, `_build` and Elia's own data (`.elia`) are, and what your commands are jailed to (DEPLOY-1, ISOL-13). **Don't change code there: make yourself a worktree first, work in it, and merge it into the trunk yourself when the change is done** (DEPLOY-28). The running server only ever loads a deploy, so this is what keeps a half-finished change out of the tree that runs:

  ```sh
  mkdir -p tmp/worktrees
  git worktree add -b "chat/$ELIA_CHAT_ID" "tmp/worktrees/$ELIA_CHAT_ID" master
  for d in deps _build; do [ -d "$d" ] && cp -a "$d" "tmp/worktrees/$ELIA_CHAT_ID/"; done
  [ -d assets/node_modules ] && cp -a assets/node_modules "tmp/worktrees/$ELIA_CHAT_ID/assets/"
  cd "tmp/worktrees/$ELIA_CHAT_ID"          # the file tools follow `cd` too
  ```

  `$ELIA_CHAT_ID` is your chat's id, which every `shell` call is given (SHELL-14), and `tmp/` is gitignored, so the worktree is never committed. Fork the trunk `master`; a sub-task forks the branch its brief names instead (its parent's, `chat/<parent id>`), so it sees what its parent has committed. If the worktree is already there — a chat resumed after a restart — reuse it (`git worktree list`, `git branch --list`).

  **The copies are the point of the recipe**: a worktree with neither fetches every dependency, compiles all of it from source and builds the browser bundle from nothing — minutes of waiting on the first command, every time — where with them the first compile is warm (this tree: ~95 MB of `deps`, ~155 MB of `_build`). They are gitignored, so they leave the worktree clean, and inside your own jail, so a copy works jailed. A copy the live tree doesn't have is skipped — a tree that has never compiled has no `_build` — and a missing copy only means a colder first compile, never a broken worktree. `assets/node_modules` is the third: without it `bin/preview` runs an npm install first (PREVIEW-14).

  Do everything in the worktree — edit, compile, `mix precommit`, `bin/preview`, commit — then merge it into the trunk from inside it (`git rebase master` first if the trunk has moved):

  ```sh
  git push . HEAD:master       # fast-forward only; it refuses anything else (DEPLOY-13)
  ```

  and remove it once the work is in, from the live tree: `git worktree remove "tmp/worktrees/$ELIA_CHAT_ID"`, then `git branch -d "chat/$ELIA_CHAT_ID"` — so a finished chat leaves neither a tree nor a branch behind. A sub-task stops before the merge: it commits on its own branch and its parent merges it (SUBTASK-23). A deploy needs the live tree *set up for deployment*: on the branch `live`, with a `master` at or ahead of it (`git checkout -b live` and `git branch master` once; `git branch -f master live` once if the trunk is behind, DEPLOY-14). Until it is set up, `master` is checked out in the live tree and git refuses to push to a checked-out branch, so the worktree route can't finish: say so and ask the user to set the tree up rather than editing the live tree itself (DEPLOY-30). The Settings page says what is missing
- Use the already included `Req` library for HTTP requests. **Avoid** `:httpoison`, `:tesla` and `:httpc`
- There is no database or Ecto. Saved conversations are files in `.elia/sessions/` (`Elia.Store`)
- Work out from the change itself whether it can break old data. For every change, ask what persisted data the code you touched reads and writes (saved conversations in `.elia/sessions/`, the settings database, saved skills/workflows, any other file that outlives the process) and whether the change alters that: a new or removed field, a different value or meaning, a renamed file or key. If it does not, say so and move on. If it does, decide which it is — the new code still reads what an older version wrote (backward compatible), or it does not and the change needs a migration (a read-time fallback, a one-off rewrite of the stored files, and a test that loads a fixture written in the old shape) — and state which in the spec or the commit message. Do not go looking through the user's data: the question is about the code's shapes, not about inspecting stored files

Read less: locate with a targeted `search_files` — it returns the matched lines with their surroundings — or `list_files` first, then read the range you need (`offset`/`limit`, or the one section of a doc) rather than whole files, and read the spec that owns the behaviour rather than every spec that mentions it.
