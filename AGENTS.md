# Elia

A local AI harness with a Phoenix LiveView chat UI. The agent works through skills and can change its own code behind guardrails. Module layout is in `README.md`. Features are specified in `specs/` (index and workflow in `specs/README.md`).

## Always

- This project is spec-driven. Before changing behaviour, update or add the spec in `specs/`. Then implement it and test each requirement you touched, citing its ID (e.g. `# SHELL-3`). Never renumber or reuse a requirement ID. When you add a spec, add it to the index table in `specs/README.md`
- After drafting or updating a spec, stop and ask the user to approve it before implementing, unless the user explicitly asked to skip the spec approval for this change. Wait for that approval before touching code or tests
- When the user asks for work to be done with sub-tasks (`spawn_task`), this chat does the planning and writes the spec itself, and sub-tasks implement only: for a job that is worth more than one step and is understood up front, draft or update the spec in `specs/` here and get the user's approval first, then spawn one sub-task per implementation step, each brief naming the spec and the requirement IDs to satisfy (and saying to test what it touches, commit and report). Keep the spec to behaviour and requirement IDs and leave the internals to the sub-task, which should raise a spec that does not fit the code as a question instead of deviating silently. A small or exploratory job — one file, one obvious behaviour, or one whose spec is its result — is done in this chat instead. Never hand the spec-writing or the planning to a sub-task
- A turn the user stops in a sub-task's chat ends that turn and never the sub-task: no result is recorded, its status stays `running`, its entry is held and the parent keeps waiting (SUBTASK-16, SUBTASK-17, `specs/subtasks.md`). Stopping a parent's turn still stops the turn of every child it has running, the same way. Don't reintroduce a "cancelled" result for a stop
- Use the `mix precommit` alias when you are done with all changes and fix any pending issues. Plain `mix precommit`: no command inherits `MIX_ENV`, so the alias's `preferred_envs` applies and it runs the tests in `test` (ISOL-24; see `docs/agents/elixir.md`). A test run is a `shell` call — there is no `run_tests` tool (VERIFY-11) — so give a suite run a longer `timeout_seconds` than the shell's default: a chat's first run in a fresh worktree compiles deps and app before its first test
- Commit to git whenever you finish a feature (after tests/`mix precommit` pass). Use a `feat: <summary>` message (or `fix:`/`docs:` etc. as appropriate), and commit only that feature's changes. Never commit a half-finished feature
- When the user states a standing preference, rule or workflow ("whenever you…", "always…", "never…", "from now on…"), record it in this file (`AGENTS.md`) in the same turn, as a bullet under "Always" (or in the matching `docs/agents/` file if it is topic-specific, then say so here). Don't just acknowledge it verbally, since you won't remember it next session. Then tell the user which file and line you updated
- In one step, ask for everything you already know you need: a step's calls run at the same time (LOOP-10), so several reads, searches or shell commands in one message cost one model round trip, not several. Batch the lookups a change needs — the topic docs its row names, the files it will touch, the greps that locate them — rather than spending a round trip per file; a batched command still gets its own jail and its own `/tmp` and pid namespace (ISOL-26, `specs/command-isolation.md`), so batching shell calls is safe
- Read, create, edit and search files with the file tools (`read_file`, `write_file`, `edit_file`, `search_files`), never with `shell` (`cat`, `sed`, `echo >`, heredocs, Python/other scripts, or `grep` to find text). `search_files` returns each match with its surrounding lines (FILE-24..FILE-30, `specs/file-tools.md`), so one call replaces `grep` plus the `read_file` that followed it. Use `shell` only to run programs such as `mix` and `git`. Shell edits skip the workspace policy and the user's file-change review
- Never prefix a shell command with `cd`. Every call already runs in the workspace root (`Elia.Skills.Shell` passes `cd: root(ctx)` to `Elia.Shell.run/2`, SHELL-2, `specs/shell-tool.md`), each call is its own `bash -c` with no state carried over, and the tool's schema has no `cwd` argument — so `cd "$(pwd)" && …`, `cd . && …` and `cd <the workspace root> && …` all change nothing and only add noise to the command the user has to approve and read. A `cd` belongs in a command only when it *changes* tree (the live tree, a sibling worktree) or when driving a `terminal`, whose session persists between sends
- Shell commands run with `bash -c` where bash is installed, otherwise POSIX `sh -c` (SHELL-2, `Elia.Shell.shell/1`), so write commands that also work under `sh`: bash-only syntax such as `${PIPESTATUS[0]}`, `[[ ... ]]`, arrays and `set -o pipefail` fails where the shell is `sh`, and after a pipeline `$?` is the last command's status (a failing `mix test | tail` looks like a success). Prefer one command that reports the status you mean, and `bash -c '...'` explicitly only when you really need bash
- The dev server never reloads code on its own: a request recompiles and loads nothing, and a change to `lib/`, `config/` or `mix.exs` reaches the running app only through a *deploy*. **When a change is done, commit it and merge your own branch into the trunk yourself**: rebase on `master` if it has moved, then `git push . HEAD:master` (fast-forward only, so `master` must be an ancestor of your branch — DEPLOY-13). Then mark the chat done with `mark_done` (`specs/chat-done.md`, DONE-6), so the chat list shows it as finished work rather than as a chat that was abandoned; a chat marked done is still resumable, and the user's next message reopens it (DONE-9). The harness never merges your branch. Deploying is the user's step, in the chat UI's Settings page: a deploy brings `master` to `live` (fast-forward, after the full test suite, then with the tree's Node packages installed and its assets rebuilt — DEPLOY-19) and loads it — "Hot reload", which recompiles and loads the live tree keeping running state, or "Restart", which restarts the server. So make all the edits for a change first, run the tests, then commit and merge; don't expect the change to be live until the user has deployed it
- When a change touches the UI (a template, `assets/css/`, `assets/js/` or a colocated hook), show the user what it looks like before it is deployed: run `bin/preview` in the chat's workspace and put the Markdown image links it prints into your reply. It screenshots the workspace's own code in a real headless browser, in the test env — no deploy, no API key — and its first run in a workspace builds assets and starts a browser, so give the `shell` call a longer `timeout_seconds` (PREVIEW-9, `specs/ui-preview.md`). Preview in dark mode at a mobile width by default — `ELIA_PREVIEW_THEME=dark ELIA_PREVIEW_WIDTH=390 bin/preview …` (PREVIEW-3, PREVIEW-13) — and take a light or desktop picture as well only when the change is about that
- A chat in Elia's own project works in its own git worktree, on branch `chat/<chat id>` forked from the trunk `master` (not from `live`), not in the live tree the server runs from (DEPLOY-1). That worktree is the chat's workspace root, and Elia's data (`.elia`, including the worktrees) sits under the live tree, `Elia.Workspace.runtime_root/0`. A deploy needs the live tree *set up for deployment*: on the branch `live`, with a `master` at or ahead of it (`git checkout -b live` and `git branch master` once; `git branch -f master live` once if the trunk is behind); until then a chat in Elia's own project works in the live tree itself, and the Settings page says what is missing (DEPLOY-14)
- Use the already included `Req` library for HTTP requests. **Avoid** `:httpoison`, `:tesla` and `:httpc`
- There is no database or Ecto. Saved conversations are files in `.elia/sessions/` (`Elia.Store`)
- Work out from the change itself whether it can break old data. For every change, ask what persisted data the code you touched reads and writes (saved conversations in `.elia/sessions/`, the settings database, saved skills/workflows, any other file that outlives the process) and whether the change alters that: a new or removed field, a different value or meaning, a renamed file or key. If it does not, say so and move on. If it does, decide which it is — the new code still reads what an older version wrote (backward compatible), or it does not and the change needs a migration (a read-time fallback, a one-off rewrite of the stored files, and a test that loads a fixture written in the old shape) — and state which in the spec or the commit message. Do not go looking through the user's data: the question is about the code's shapes, not about inspecting stored files

## Read before you…

This file (`AGENTS.md`) is injected into the system prompt. The files below are not, so open the ones your change matches — only those, and in one step (several `read_file` calls in one message). Read less: locate with a targeted `search_files` — it returns the matched lines with their surroundings — or `list_files` first, then read the range you need (`offset`/`limit`, or the one section of a doc) rather than whole files, and read the spec that owns the behaviour rather than every spec that mentions it.
