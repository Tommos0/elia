# Elia

A local AI harness with a Phoenix LiveView chat UI. The agent works through skills and can change its own code behind guardrails. Module layout is in `README.md`. Features are specified in `specs/` (index and workflow in `specs/README.md`).

## Always

- This project is spec-driven. Before changing behaviour, update or add the spec in `specs/`. Then implement it and test each requirement you touched, citing its ID (e.g. `# SHELL-3`). Never renumber or reuse a requirement ID. When you add a spec, add it to the index table in `specs/README.md`. The rest of what the corpus must hold to — one word for `Status:`, a section outside the allowed shape, an ID defined twice, a citation of an ID no spec defines — is `specs/README.md`'s rules (SPEC), and `test/elia/spec_hygiene_test.exs` fails the suite on it, so a violation is a test failure rather than a review comment. Every requirement must also be accounted for by a test file that is there or by a `No test:` line in its own spec saying why (TRACE, `specs/test-traceability.md`), which `test/elia/spec_tests_test.exs` fails the suite on
- Before you draft a spec change, reserve the requirement IDs you are about to use: `bin/reserve <PREFIX> <count>` prints the numbers to draft with, so two chats drafting at once don't take the same one (SPEC-19). It keeps its reservations in the repository's git directory, and where it can't run — no store, an unwritable one — you take the next unused number as SPEC-3 says (SPEC-25).
- After drafting or updating a spec, stop and ask the user to approve it before implementing, unless the user explicitly asked to skip the spec approval for this change. Wait for that approval before touching code or tests
- A spec's `Status:` line moves with the code, in the same commit: when a change makes a spec's requirements true, flip it to `Status: Implemented`; when its last live requirement is retired, `Status: Retired`, and its index row's summary says so (SPEC-5, SPEC-7). A spec written ahead of its code stays `Draft` until the code lands, and one whose code has already landed is a stale `Draft` to fix rather than leave
- When the user asks for work to be done with sub-tasks (`spawn_task`), this chat does the planning and either chat may write the spec. Planning is mine: split the job into steps and check each one is independent before spawning — a sub-task sees neither this chat nor its siblings, so a step is independent only when its brief alone is enough to see it finished, tested and committed: no decision I haven't made, no requirement resting on work another step has not landed, and no spec of its own that a sibling's findings would change. A step that fails that check is done here instead, split further, or ordered behind the step it needs. The spec in `specs/` is drafted or updated and approved before the code it names is written (the approval given here or in the sub-task's own chat, unless the user said to skip it for this change). Then spawn one sub-task per implementation step, its brief naming the spec and the requirement IDs to satisfy and saying to test what it touches, commit and report. Keep the spec to behaviour and IDs and leave the internals to the sub-task, which should raise a spec that does not fit the code as a question instead of deviating silently. What is never handed over is a step that isn't independent — that is the parent's call, made before the spawn — and a small or exploratory job, one file or one obvious behaviour or one whose spec is its result, is done in this chat.
- Number the sub-tasks you spawn and hand each brief over as a file rather than in the `spawn_task` text — `.tasks/<your chat id>/<n>/brief.md`, its report beside it — as the `tasks` skill's section says (SUBTASK-37, SUBTASK-38); the id is your own chat's, so two chats' numbering never meets. Neither file is work, so commit neither (`.tasks/` is ignored here).
- Nothing ends a sub-task but its own chat being marked done (SUBTASK-33) — not the end of a turn, not a limit, not a stopped turn, not a dead session — and stopping a parent's turn stops the turn of every child it has running, the same way. A sub-task is otherwise an ordinary chat: its own status, no limits, lock, listing or record of what it changed of its own, and the result `await_task` gives is the `{"task_id", "summary"}` the harness derives (SUBTASK-9); don't reintroduce a task status vocabulary or a registry (see `docs/agents/harness.md`).
- In a sub-task chat, "done" means something smaller than it does here: the work is committed on your own branch (`chat/<sub-task id>`, DEPLOY-28), not landed on `master` — the parent merges it when it wants the work (SUBTASK-23) — and calling `mark_done` is your last act, because it is what ends the task and reports your result. So commit before you mark the chat done, and say what you did in your last message, where anything the user must settle also goes
- Finish with the `mix precommit` alias and fix what it finds (plain `mix precommit`: no command inherits `MIX_ENV`, so it runs the tests in `test`, ISOL-24). A test run is a `shell` call — there is no `run_tests` tool (VERIFY-11) — so give it a longer `timeout_seconds` than the shell's default (300s, up to 1800, SHELL-10): a chat's first run in a fresh worktree compiles deps and app before its first test. Runs keep their own workspace, settings database and temp directory (SUITE-1, SUITE-11), so concurrent runs don't corrupt each other; what you still share is the endpoint port, so a run that binds one — a browser run, `bin/preview` — needs its own `ELIA_TEST_PORT`.
- Running the suite is a judgement, not a ritual: a change you can call safe without running anything — a doc, spec or comment edit, a rename with nothing behind it — skips it, and one sentence in your last message saying why is the whole record, with no other paperwork. Anything that changes behaviour, anything you are not sure of, and anything that adds or moves requirement IDs still gets the suite, since the hygiene and traceability lints are what a run would have caught. A skip relaxes the run only: the tests a requirement needs are still written (TRACE), and the change is still committed and merged. A brief you write may hand this judgement to its sub-task, asking it to say in `report.md` why the skip was safe.
- Commit to git whenever you finish a feature (after tests/`mix precommit` pass, or after the safe skip the bullet above allows). Use a `feat: <summary>` message (or `fix:`/`docs:` etc. as appropriate), and commit only that feature's changes. Never commit a half-finished feature
- When the user states a standing preference, rule or workflow ("whenever you…", "always…", "never…", "from now on…"), record it in this file (`AGENTS.md`) in the same turn, as a bullet under "Always" (or in the matching `docs/agents/` file if it is topic-specific, then say so here). Don't just acknowledge it verbally, since you won't remember it next session. Then tell the user which file and line you updated
- In one step, ask for everything you already know you need: a step's calls run at the same time (LOOP-10), so several reads, searches or shell commands in one message cost one model round trip, not several. Batch the lookups a change needs — the topic docs its row names, the files it will touch, the greps that locate them — rather than a round trip per file; batching shell calls is safe, since each still gets its own jail and its own `/tmp` and pid namespace (ISOL-2, ISOL-9).
- Look before you work it out: before investigating how something behaves or how to do a job in this tree, spend one step on the cheap lookups — `search_chats` on the words of the question (HIST-1, `specs/chat-history.md`) and the spec that owns the behaviour (`specs/README.md`'s index). An earlier chat or a spec has usually settled it already, and re-deriving it costs many round trips: say in the reply which earlier chat or spec you found, or that there was none.
- Record what cost you real effort and is not behaviour — a command that only works in one form, a test that fails for a reason of its own, where a thing lives, a path that didn't work — in the same turn, in the topic doc the "Read before you…" table names (`docs/agents/`), or in this file when it is about the tree as a whole: a line or two, in the place the next chat will look. The spec corpus holds behaviour; this is the rest of what you learned, so the next chat starts from it instead of from nothing.
- Read, create, edit, search and delete files with the `shell` (SHELL-15): `grep -n` finds text, `sed -n '<first>,<last>p'` reads a range, `cat` a short file, and a heredoc (`<<'EOF'`, quoted so nothing is expanded), `sed -i` or `patch` changes one — and since the command the user approves is the change, make it one readable command that says what it changes and edit the lines you have read rather than rewriting a file whole. A multi-hunk `patch` stops at the first hunk it can't place — the hunks before it stay applied and the rest are silently missing — so give every hunk its context lines and check with `git diff`, or edit a multi-line block by exact-string replacement that fails when the text matches zero times or twice.
- Never prefix a shell command with `cd`: every call already runs in the chat's working directory (SHELL-2, WD-9), each is its own `bash -c` with no state carried over, and the tool's schema has no `cwd` argument, so `cd "$(pwd)" && …` and `cd . && …` change nothing and only add noise to the command the user approves. To work somewhere else, call the `cd` tool once (WD-1, WD-3). A `cd` belongs in a command only when it *changes* tree for that one command (the live tree, a sibling worktree) or when driving a `terminal`, whose session persists between sends.

- A change reaches the running app only through a *deploy* (DEPLOY-8): the dev server never reloads code on its own and no request recompiles or loads anything. **When a change is done, commit it in your worktree and merge that branch into the trunk yourself** — the recipe above (DEPLOY-13) — then call `mark_done` (`specs/chat-done.md`, DONE-6) so the chat list shows finished work rather than an abandoned chat; a done chat is still resumable, and the user's next message reopens it (DONE-9). Deploying is the user's step, in the chat UI's Settings page: it brings `master` to `live` after the full suite and loads it (DEPLOY-19), by "Hot reload" (recompiling and loading the live tree, keeping running state) or "Restart". The harness never merges your branch, so don't expect the change to be live until the user has deployed it.
- When a change touches the UI (a template, `assets/css/`, `assets/js/` or a colocated hook), show the user what it looks like before it is deployed: `ELIA_PREVIEW_THEME=dark ELIA_PREVIEW_WIDTH=430 bin/preview …` in the chat's workspace, giving the `shell` call a longer `timeout_seconds` (its first run in a workspace builds assets and starts a browser), then put the Markdown image links it prints into your reply. It screenshots the workspace's own code in a real headless browser, in the test env — no deploy, no API key (PREVIEW-9, `specs/ui-preview.md`). A light or desktop picture as well only when the change is about that (PREVIEW-3, PREVIEW-13).
- A chat in Elia's own project works in the project's folder — the live tree the server runs from, where your files, `deps`, `_build` and Elia's own data (`.elia`) are, and what your commands are jailed to (DEPLOY-1, ISOL-13). **Don't write anything there — the live tree stays clean: make yourself a worktree first, work in it, and merge it into the trunk yourself when the change is done** (DEPLOY-28). The running server only ever loads a deploy, so this is what keeps a half-finished change out of the tree that runs — and a deploy puts whatever is uncommitted in the live tree aside in a git stash before it merges (DEPLOY-37), so an edit left there does not block the user's deploy: it quietly leaves the tree you are working in and waits in the stash (`git stash list`) for someone to notice.

  ```sh
  mkdir -p tmp/worktrees
  git worktree add -b "chat/$ELIA_CHAT_ID" "tmp/worktrees/$ELIA_CHAT_ID" master
  for d in deps _build; do [ -d "$d" ] && cp -a "$d" "tmp/worktrees/$ELIA_CHAT_ID/"; done
  [ -d assets/node_modules ] && cp -a assets/node_modules "tmp/worktrees/$ELIA_CHAT_ID/assets/"
  cd "tmp/worktrees/$ELIA_CHAT_ID"          # what a command's paths resolve against follows `cd` too
  ```

  `$ELIA_CHAT_ID` is your chat's id, which every `shell` call is given (SHELL-14), and `tmp/` is gitignored, so the worktree is never committed. Fork the trunk `master`; a sub-task forks the branch its brief names instead (its parent's, `chat/<parent id>`), so it sees what its parent has committed. If the worktree is already there — a chat resumed after a restart — reuse it (`git worktree list`, `git branch --list`). The copies are what make its first compile warm instead of fetching and building every dependency from nothing (`docs/agents/harness.md`).

  Do everything in the worktree — edit, compile, `mix precommit`, `bin/preview`, commit — then merge it into the trunk from inside it (`git rebase master` first if the trunk has moved):

  ```sh
  git push . HEAD:master       # fast-forward only; it refuses anything else (DEPLOY-13)
  ```

  and remove it once the work is in, from the live tree: `git worktree remove "tmp/worktrees/$ELIA_CHAT_ID"`, then `git branch -D "chat/$ELIA_CHAT_ID"` (the merge went into `master`, not the checked-out `live`, so `-d` refuses until a deploy moves `live` up to it). Check `git status --porcelain` in the live tree before the commit and again before the merge: it says nothing when the tree is clean, and a change someone else left there is theirs, not yours to commit. A sub-task stops before the merge: it commits on its own branch and its parent merges it (SUBTASK-23). When there is no worktree to have — the trunk `master` is checked out in the live tree, so git refuses to push to it — this route can't finish: say so and ask the user to set the tree up rather than editing the live tree itself (DEPLOY-30, DEPLOY-14; the Settings page says what is missing).
- Use the already included `Req` library for HTTP requests. **Avoid** `:httpoison`, `:tesla` and `:httpc`, and note there is no database or Ecto: saved conversations are files in `.elia/sessions/` (`Elia.Store`).

- Work out from the change itself whether it can break old data: which persisted data the code you touched reads and writes — saved conversations in `.elia/sessions/`, the settings database, saved skills and workflows, any other file that outlives the process — and whether the change alters that: a new or removed field, a different value or meaning, a renamed file or key. If it does not, say so and move on. If it does, decide which it is and state it in the spec or the commit message: the new code still reads what an older version wrote (backward compatible), or it does not and the change needs a migration — a read-time fallback, a one-off rewrite of the stored files, and a test that loads a fixture written in the old shape. The question is about the code's shapes, not about inspecting stored files: don't go looking through the user's data (`docs/agents/elixir.md` has the worked examples).

## Read before you…

This file (`AGENTS.md`) is injected into the system prompt. The files below are not, so open the ones your change matches — only those, and in one step (several reads in one message). Read less: locate with a targeted `grep -n` first, then read the range you need (`sed -n '<first>,<last>p'`, or the one section of a doc) rather than whole files, and read the spec that owns the behaviour rather than every spec that mentions it.
